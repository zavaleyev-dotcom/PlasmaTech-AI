# Архитектура PlasmaTech AI

## Текущее поведение

Существующие страницы и общие стили сохранены. SciFinder открывает рабочий
библиографический поиск через Crossref. Остальные пять карточек по-прежнему
открывают демо-диалог со ссылкой на отдельную страницу. Запросы не сохраняются
в базе данных; поисковые параметры SciFinder передаются Crossref сервером Next.js.

| Модуль | Страница | Каталог в src/modules/workspace |
| --- | --- | --- |
| SciFinder | /workspace/scifinder | scifinder |
| TechDoc Assistant | /workspace/techdoc-assistant | techdoc-assistant |
| НаучПисатель | /workspace/scientific-writer | scientific-writer |
| Equipment Selector | /workspace/equipment-selector | equipment-selector |
| Techno-Economic Assessment | /workspace/techno-economic-assessment | techno-economic-assessment |
| Engineering Calculators | /workspace/engineering-calculators | engineering-calculators |

Общий маршрут `src/app/workspace/[module]/page.tsx` создает шесть отдельных страниц
из реестра, с индивидуальными метаданными. Неизвестные модули возвращают 404.
Описания и учебные результаты остаются в `src/lib/content.ts` — едином источнике
текущего контента. Каждый каталог модуля содержит его идентификатор, slug и пример
задачи; там же позже разместятся специфичные схемы входных данных и сценарии.

## Слои и направления зависимостей

- `components/workspace-module.tsx`: форма, состояния ожидания, результата и ошибки.
- `modules/workspace`: определения шести модулей, типы и реестр маршрутов.
- `services/workspace`: контракт провайдера, демо-реализация и явная композиция.
- `agents`: определения агентов и контракт будущего исполнителя сценариев.
- `skills`: прикладные инструкции для будущих агентов (не навыки Codex).
- `calculators`: контракт детерминированных расчетов с единицами и допущениями.
- `knowledge-base`: документы с происхождением и контракт поиска.
- `database`: модели сохраненных запусков и интерфейс репозитория.
- `integrations`: контракты OpenAI, MCP, Google Drive, научных баз,
  PostgreSQL и Supabase. Crossref и OpenAlex — рабочие серверные адаптеры,
  оба подключены в серверную композицию (`src/services/scientific-search/index.ts`)
  и используются как по отдельности, так и вместе в режиме `combined`.
  Другие интеграции остаются заготовками.

Для пяти демо-модулей: UI → workspaceService → demoProvider. Старый `lib/demo-provider.ts`
сохранен как совместимый реэкспорт, поэтому диалоги используют тот же провайдер.

В дальнейшем: UI → клиентский HTTP-провайдер → серверный Route Handler →
сервис сценария → агент / навык / калькулятор → серверные адаптеры.
Знания поступают через KnowledgeSearch, сохранение — через WorkspaceRunRepository.
Типы интеграций не предполагают конкретных SDK или их версий.

## SciFinder Search Pipeline

```text
User Query
  → SciFinder UI
  → Next.js API Route
  → ScientificSourceProvider(s): Crossref и/или OpenAlex (по выбору источника,
    оба параллельно при source=combined)
  → normalization
  → deduplication
  → filters
  → results
```

### Файлы и границы

- `src/components/scifinder/search.tsx`: форма, поиск, пустое состояние, ошибки,
  индикатор, повтор запроса, счётчики. Запрос только к собственному API.
- `src/components/scifinder/publication-card.tsx`: только общий тип `Publication`.
- `src/components/scifinder/search.module.css`: стили, ограниченные SciFinder.
- `src/app/api/scifinder/search/route.ts`: POST, ограничение тела 16 KiB,
  валидация и структурированные ошибки; `Cache-Control: no-store`.
- `src/services/scientific-search/types.ts`: `Publication`, запрос, фильтры,
  `ScientificSourceProvider`, результат и ошибка.
- `validation.ts`: длины, диапазон лет, допустимые лимиты/типы/источники и DOI.
- `index.ts`: серверная композиция адаптеров; `pipeline.ts`: общая обработка.
- `normalization.ts`, `deduplicate.ts`, `filters.ts`: общие чистые функции.
- `src/integrations/crossref`: HTTP-адаптер и нормализация внешней схемы.
- `src/integrations/openalex`: рабочий HTTP-адаптер; работает и без ключа
  (keyless-режим), `OPENALEX_API_KEY` только повышает лимит запросов.

Серверные точки входа импортируют `server-only`. UI получает сериализуемую
модель и не зависит от формата ответа Crossref, SDK или переменных окружения.

### Запросы, ошибки и ограничения

Crossref использует `/works?query.bibliographic=...` и `/works/{encoded DOI}`.
Хост фиксирован; DOI и параметры кодируются. Параметры выбора числа результатов,
года, типа и наличия abstract передаются источнику, затем фильтры повторно
применяются к нормализованным данным. Crossref регистрирует DOI, поэтому фильтр
наличия DOI обычно не уменьшает выборку этого источника.

Точный DOI не использует текстовый запрос. Crossref 404 для DOI — пустая выдача,
а не ошибка приложения; DOI другой регистрационной организации может не найтись.

Один внешний запрос имеет тайм-аут 20 секунд; браузер ждёт не более 25 секунд.
Ограничение источника 429, HTTP-сбой, некорректный ответ и тайм-аут преобразуются
в понятные сообщения. Кнопка повтора повторяет последний отправленный запрос.
Автоматических бесконечных повторов и скрытой загрузки следующих страниц нет.
Выход со страницы отменяет ожидание браузера. Ответы не кэшируются приложением.

При `source=combined` (`src/services/scientific-search/index.ts`, `pipeline.ts`)
Crossref и OpenAlex запрашиваются параллельно (`Promise.allSettled`). Успешные
источники объединяются, проходят общие дедупликацию и фильтры; отказавший
источник не прерывает поиск — его ошибка попадает в `sourceStats`/`warnings`,
а результат другого источника возвращается. Поиск завершается ошибкой только
если отказали все запрошенные источники.

`total` — сумма чисел совпадений, сообщённых каждым источником, который
ответил успешно (`sourceStats`, `pipeline.ts`); для одиночного источника
это его собственный `total`, для `combined` — сумма по Crossref и OpenAlex,
без учёта отказавших источников. `retrieved` — число загруженных записей;
`duplicatesRemoved`, `filteredOut` и `returned` показывают обработку первой
выборки. `limit` ограничивает её 10/25/50 записями. Локальные фильтры могут
уменьшить количество: сервис не выдаёт первую страницу за полный поиск по
всем базам.

### Общая модель и достоверность

`Publication`: id, title, authors, year, journal, doi, abstract, publisher, url,
type, source, sources, openAccess. Отсутствующие сведения — `null` или пустой
список авторов; отсутствующее название отображается как «Без названия».
Источники будущих адаптеров: crossref, openalex, semantic-scholar, google-drive, local.

Abstract очищается от XML/JATS-тегов и выводится как текст; HTML не исполняется.
Ссылки допускают только HTTP/HTTPS без встроенных учётных данных. DOI ведёт
на doi.org. Дата берётся из published, с fallback на issued/print/online.
`openAccess` у Crossref — `null`: наличие лицензии само по себе недостаточно.
Признак peer-reviewed не придумывается. Нет AI-аннотаций, выводов или скачивания PDF.

### Дедупликация

1. Нормализованный DOI (регистр, префикс doi:, URL резолвера).
2. Если хотя бы у одной записи DOI отсутствует — нормализованное название + год.
3. Разные известные DOI никогда не сливаются. Неоднозначные совпадения названия
   с несколькими DOI сохраняются отдельно. Неизвестный год не даёт надёжного ключа.
4. При объединении заполняются отсутствующие поля, объединяются источники,
   а релевантность складывается из релевантности обеих записей; порядок
   первой записи используется только как внутренний тай-брейк дедупликации,
   а не как окончательный порядок выдачи — после дедупликации результат
   ещё проходит `sortPublications` (`sort.ts`), которая и определяет
   итоговый порядок по выбранному критерию (по умолчанию — по этой же
   объединённой релевантности).

## Моя библиотека — локальный индекс PDF

Страница `/my-library` дополняет существующую `/library`, не заменяя её содержимое.
Она использует `GET /api/library` для чтения индекса и `POST /api/library` для
запуска фонового обновления. Прогресс опрашивается во время сканирования.
Этот режим рассчитан на один локальный процесс Next.js, не на serverless hosting.
При остановке сервера сканирование прекращается; предыдущий индекс сохраняется.

Конфигурация: `SCIENTIFIC_LIBRARY_PATH` в игнорируемом `.env.local`. Реальный путь
не должен попадать в Git. Индекс хранится в `.local-data/scientific-library/index.json`
в корне проекта, отдельно от PDF; весь `.local-data/` также исключён из Git.
Индекс содержит приватные абсолютные пути, которые API не возвращает браузеру.

Pipeline: configured root → recursive PDF discovery → safe read → isolated PDF
parser → bibliographic metadata / filename fallback → atomic local JSON index
→ client-side search, filters, sorting, pagination.

- Путь никогда не принимается от клиента. API доступен только для loopback Host;
  чужой Origin и cross-site запросы отклоняются. Сервер запускать на 127.0.0.1.
- Символические ссылки не обходятся. Проверяются canonical containment,
  компоненты пути, O_NOFOLLOW и идентичность открытого файла. Чтение только O_RDONLY.
- PDF разбираются в двух отдельных дочерних процессах, по 20 секунд на документ,
  не более 128 МБ на файл. Превышения отмечаются как ошибки; запись по имени файла
  остаётся в индексе. PDF больше лимита не разбираются, но также учитываются.
- Используется pdf-parse; читаются Info/XMP и текст первых двух страниц, без OCR.
  Название/авторы — только метаданные, DOI — единственный однозначный кандидат
  из метаданных или первых страниц до раздела References. Год — только явно
  заданная дата публикации; CreationDate/ModDate не считаются годом публикации.
  PDF-метаданные могут быть заполнены издателем неточно, внешняя проверка не выполняется.
- Неизвестные значения остаются null/пустыми. Тип документа определяется по
  ближайшей распознаваемой папке, а не по AI-классификации содержимого.
- Повторное сканирование использует размер и mtime для неизменённых документов,
  повторяет ошибочные чтения, удаляет отсутствующие записи только из индекса.
  При ошибке доступа к каталогу прежние записи этого каталога сохраняются.
- Запись индекса атомарная, файл с правами 0600; одновременно запускается один job.
  Полный текст PDF не сохраняется. Запросов к Crossref/OpenAlex при сканировании нет.
  Защита от повторного запуска этого job хранится только в памяти процесса
  (`globalThis`, `src/services/local-library/index.ts`), в отличие от текстового
  индекса ниже, где статус и PID пишутся в SQLite. Это осознанное ограничение
  текущего single-process режима: при одновременном запуске нескольких процессов
  Next.js на одной библиотеке (что архитектурой не предполагается) защита от
  двух параллельных сканирований метаданных не действует между процессами.
  Persistent cross-process блокировка для этого job пока не реализована.
- Интеграции SciFinder не изменены. RAG, embeddings, vector database и AI-анализ
  не подключены. Служебные файлы в исходных папках не создаются.

Тесты: `tests/local-library.test.ts` — рекурсия, пути/ссылки, реальный PDF parser,
повреждённые файлы, обновление/удаление из индекса, фильтры, сортировка, API isolation.


## Этап 2: локальный текстовый индекс

Отдельная подсистема `src/services/library-text` использует SQLite FTS5 через
встроенный `node:sqlite` (Node.js 22.13+; проверено на Node.js 25.8).
Это обычный лексический индекс, без embeddings, vector database и LLM API.

Хранилище: `.local-data/scientific-library/text/index.sqlite`, включая приватные
WAL/SHM-файлы в том же каталоге. Всё дерево `.local-data/` исключено из Git.
Существующий `metadata index.json` эта подсистема только читает, не переписывает.

Pipeline: явный запуск → рекурсивный список PDF → проверка mtime/размера/версии
обработчика → безопасное чтение → PDF-процесс → полный текст по физическим
страницам → фрагменты → транзакция документа в SQLite → FTS5/BM25 → результаты.

### Данные и ограничения

Таблица documents хранит id библиотеки, относительный путь, имя файла,
библиографические метаданные из metadata index (либо имя нового файла), полный
извлечённый текст, количество страниц/символов/слов, статус/ошибку, extractedAt,
mtime, размер, SHA-256 обработанного PDF и версию алгоритма. Текст новых/изменённых
файлов обновляется; неизменённые успешные/пропущенные файлы не разбираются заново.
Ошибки чтения повторяются при явном обновлении. Изменение файла без изменения
размера и mtime не обнаруживается быстрым проходом: хеш считается при извлечении.
Библиографические поля берутся из существующего индекса метаданных; его можно
обновить прежней кнопкой независимо от текста.

Таблица chunks содержит стабильный SHA-256 id (document id + позиция + текст),
ссылку на документ, порядковый номер, текст, число слов и физические страницы
начала/конца. Цель — 1200 слов, верхняя граница 1500; последние фрагменты короче.
Overlap — до 150 слов по целым предложениям (примерно 12.5%); длинные предложения
могут уменьшать перекрытие. Только предложения длиннее целевого фрагмента делятся
по словам. Границы страниц сохраняются; это номера страниц PDF, не печатная нумерация.

Два локальных PDF-процесса одновременно, каждый до 512 МБ JS heap, 90 секунд на
документ. Процесс перезапускается каждые 20 документов. PDF более 128 МБ, более
5000 страниц или более 20 млн символов пропускаются с причиной. Скан без текста
имеет status=no_text. OCR не запускается. Текстовый слой PDF может содержать
ошибки кодировки/порядка чтения; полнота здесь означает обход всех страниц,
не восстановление содержимого изображений, таблиц или формул.

Один документ записывается атомарно вместе с chunks и FTS. Обработка тысяч PDF
не загружает всю библиотеку в RAM. Незавершённый документ не записывается при
остановке; завершённые остаются. Отдельные ошибки не прерывают библиотеку.
Недоступные каталоги сохраняют прежние записи; действительно отсутствующие PDF
удаляются только из текстового индекса после полного успешного обхода.

### API и UI

- `GET /api/library/text`: статистика, ход обработки, ошибки/пропуски.
- `POST /api/library/text`: явное обновление; повторный запуск не создаёт второй job.
- `DELETE /api/library/text`: запрос безопасной остановки (данные не удаляет).
- `GET /api/library/text?q=…&offset=…`: лексический поиск по chunks, 20 результатов
  на страницу (первые 10020 фрагментов). Слова соединены AND; двойные кавычки —
  точная фраза. Ввод преобразуется в литералы, FTS/SQL-синтаксис не исполняется.
- `GET /api/library/pdf?id=…`: поток оригинального PDF по известному id, включая
  HTTP Range. Произвольный путь не принимается; containment, O_NOFOLLOW и inode
  проверяются заново. PDF открывается браузером, файл не изменяется/не копируется.

API ограничены loopback Host/same Origin, без внешней публикации локальных данных.
Текстовые фрагменты выводятся как обычный React-текст, без HTML интерпретации.
Страница «Моя библиотека» сохраняет прежний режим и добавляет переключатель
«Поиск по содержимому», кнопки обновления/остановки и ссылки на PDF.
При старте приложения индексирование не запускается.

Прогресс и PID процесса хранятся в SQLite, поэтому CLI и UI видят одну работу.
После завершения процесса ранее записанные документы повторно не извлекаются.
Локальная архитектура рассчитана на один компьютер, а не serverless deployment.

**Известное ограничение: блокировка от повторного запуска работает только в
пределах одного процесса/машины.** `claim()` проверяет живость предыдущего
запуска через `process.kill(pid, 0)` — это системный вызов ОС, который имеет
смысл только для PID на ТОЙ ЖЕ машине; он не может подтвердить или опровергнуть
существование процесса на другом хосте/контейнере. Если `.local-data`
когда-либо окажется на сетевой файловой системе, доступной из двух разных
процессов на РАЗНЫХ машинах одновременно, эта проверка не защитит от двух
параллельных запусков (совпадение PID было бы случайным, а само число PID с
другого хоста в принципе непроверяемо). То же самое верно для аналогичного
`claim()`/`pid` в `src/services/embeddings/store.ts`. Сейчас это не
проблема (единственный сценарий использования — один компьютер, файлы строго
локальные), поэтому распределённая/persistent-lock защита (сетевой lock,
lease с TTL и т.п.) сознательно НЕ реализована в этом раунде — это осознанное
ограничение, а не пропущенный кейс, и оно фиксируется здесь именно для того,
чтобы не быть переоткрытым как "баг" при последующем рефакторинге.

После проверки:

## Этап 3: «Спросить библиотеку» (первый этап RAG, без embeddings)

Новая подсистема `src/services/rag` строит retrieval-augmented ответы поверх уже
существующего FTS5-индекса из этапа 2 — как единственного retrieval-слоя. Ни
индексирование, ни SQLite-схема, ни `TextStore.search()` этим этапом не
изменены; `rag` читает полный текст чанка напрямую через уже публичное поле
`store.db` (`SELECT text FROM chunks WHERE id=?`), не добавляя новых методов в
`library-text`. Embeddings и vector database не подключены; интерфейсы
намеренно рассчитаны на то, чтобы retrieval-провайдер на эмбеддингах можно было
подключить позже отдельно, не трогая context-builder, промпт, валидацию цитат
и answer-provider.

Pipeline: вопрос пользователя → `retrieveChunks` (ключевые слова → `TextStore.search()`,
при пустом строгом AND — fallback на объединение независимых запросов по каждому
слову, reciprocal-rank fusion как в `scientific-search/pipeline.ts`) → `buildContext`
(ограниченный по размеру блок RETRIEVED DOCUMENTS с индексами `[1]`, `[2]`, …) →
`AnswerProvider.generate()` → проверка цитат → `AnswerResult`.

- `src/services/rag/retrieve.ts`: вопрос → термины (стоп-слова RU/EN отброшены,
  цитаты в кавычках сохраняются как фразы) → один или несколько вызовов
  существующего `store.search()`.
- `src/services/rag/context.ts`: `buildContext` — жёсткий предел размера контекста
  (`MAX_CONTEXT_CHARS`) и предел на один чанк (`MAX_CHUNK_CHARS_IN_CONTEXT`);
  всегда включает хотя бы самый релевантный чанк, даже если он один больше лимита.
- `src/services/rag/prompt.ts`: SYSTEM/USER QUESTION/RETRIEVED DOCUMENTS — три
  явно разделённых секции одного запроса к модели.
- `src/services/rag/citations.ts`: `hasOnlyKnownCitations` — ответ, ссылающийся
  на номер `[n]`, которого нет в реальных результатах поиска, отклоняется целиком
  (не редактируется по частям).
- `src/services/rag/providers/`: интерфейс `AnswerProvider` (`configured()` +
  `generate()`), `unconfiguredProvider` по умолчанию, рабочий `OpenAIAnswerProvider`
  (инжектируемый `fetch`, тайм-аут, структурные ошибки — по образцу
  `CrossrefProvider`/`OpenAlexProvider`). Anthropic и локальная модель подключаются
  той же реализацией интерфейса в `providers/index.ts`.
- `src/app/api/library/ask/route.ts`: `POST`, ограничение тела 8 KiB, тот же
  `isLocalLibraryRequest`, что и у остальных API «Моей библиотеки».

### Защита от prompt injection и от несуществующих цитат

Текст PDF — недоверенные данные, никогда не инструкции. `buildContext` заменяет
буквальные последовательности `<<<`/`>>>` внутри текста чанка на визуально
похожие, но безвредные символы (`‹‹‹`/`›››`), поэтому внедрённый в PDF текст не
может подделать закрывающий разделитель и «выйти» за пределы блока RETRIEVED
DOCUMENTS. SYSTEM-инструкция отдельно требует игнорировать любые команды внутри
RETRIEVED DOCUMENTS. Даже если бы это не сработало, единственное, на что способен
внедрённый текст — исказить текст ответа как строку: RAG не выполняет команд из
PDF, не обращается к файловой системе или сети по указанию модели, а всякий
ответ, ссылающийся на номер `[n]` вне реального списка источников, отбрасывается
целиком через `hasOnlyKnownCitations`.

### Поведение без настроенного answer provider

Если `OPENAI_API_KEY` не задан, `getAnswerProvider()` возвращает
`unconfiguredProvider`; `askLibrary` не вызывает генерацию вовсе, `AnswerResult`
получает `configured:false`, а UI показывает найденные источники и фрагменты
с объяснением, что генерация не настроена. Пустой retrieval возвращает точную
фразу «В проиндексированной библиотеке недостаточно данных для уверенного
ответа.» без обращения к провайдеру. Ошибка провайдера (сеть, тайм-аут,
невалидный ответ) не приводит к падению — показываются те же источники.

### UI и диагностика

Вкладка «Спросить библиотеку» в `src/components/local-library/ask.tsx` рядом с
«Поиск по метаданным»/«Поиск по содержимому»: вопрос, выбор числа фрагментов
(4/8/12/20, по умолчанию 8, `MAX_RETRIEVAL_LIMIT=20`), ответ с `[n]`, блок
«Источники» (title/authors/year/DOI/filename/страницы/«Открыть PDF» — та же
ссылка `/api/library/pdf?id=`, что и в поиске по содержимому), переключатель
«Показать найденные фрагменты». В `NODE_ENV=development` ответ API дополнительно
содержит `diagnostics`: число найденных чанков, использованные документы,
относительный score по чанкам, размер контекста и было-ли усечение, время
retrieval и generation.

Тесты: `tests/rag.test.ts` — извлечение терминов, retrieval по вопросу и по
нескольким документам, пустой результат и точная фраза «недостаточно данных»,
корректные и некорректные (несуществующий номер) цитаты, prompt injection внутри
текста PDF, отсутствие/ошибка answer provider, переполненный контекст, открытие
PDF по id из цитаты через существующий защищённый эндпоинт и отклонение
подделанного id, валидация входа и защита API-роута.

### Следующий этап (реализован ниже)

Векторный индекс, embedding-провайдер, семантический retrieval и гибридный
FTS5+vector ranking реализованы — см. «Этап 4» ниже. Не реализовано намеренно:
Anthropic/локальный answer-provider (тривиально добавляются той же реализацией
`AnswerProvider`), персистентность истории вопросов/ответов, полный embedding
build всей библиотеки, OCR, reranker LLM, knowledge graph.


## Этап 4: semantic embeddings и hybrid retrieval (FTS5 + vectors)

Новый, полностью отдельный модуль `src/services/embeddings` — свой SQLite-файл
(`.local-data/scientific-library/embeddings/index.sqlite`, уже покрыт общим
правилом `.local-data/` в `.gitignore`), своя схема, независимая от FTS5-индекса
`library-text`. Модуль только ЧИТАЕТ таблицу `chunks` существующего текстового
индекса (через уже публичное поле `store.db`, как и `rag/hydrate.ts`); ни схема,
ни код `library-text` не менялись.

### EmbeddingProvider

```ts
interface EmbeddingProvider {
  readonly id: string; readonly model: string; readonly dimension: number;
  configured(): boolean;
  embedDocuments(texts: readonly string[]): Promise<Float32Array[]>;
  embedQuery(text: string): Promise<Float32Array>;
  readonly outboundDataDescription: string; // что покидает машину при использовании
}
```

Реализации: `DeterministicEmbeddingProvider` (без сети и ключей, воспроизводимые
unit-векторы через SHA-256; поддерживает `failOn`/`emptyVectorOn`/
`wrongDimensionOn` для тестов сбоев) и `OpenAIEmbeddingProvider` (`/v1/embeddings`,
DI `fetch`, тайм-аут, строгая проверка `Content-Type: application/json`,
нормализованные ошибки — по образцу `OpenAIAnswerProvider`).

`getEmbeddingProvider()` возвращает провайдер **только** если явно задан
`EMBEDDING_PROVIDER=openai` — наличия `OPENAI_API_KEY` (уже используемого RAG
answer-provider'ом) для этого недостаточно: это осознанное разделение, потому что
эмбеддинг всей библиотеки — принципиально другой по объёму отправляемых данных
сценарий, чем небольшой контекст одного вопроса. Полный embedding build не
запускается автоматически ни при каких условиях в этой версии — только через
`scripts/index-embeddings.ts`, и только с `--sample <n>` (без `--all`; жёсткий
потолок `MAX_SAMPLE_SIZE=300` применяется даже к ошибочно большому числу).

### Хранилище эмбеддингов

Таблица `embeddings`: `chunkId` (PK), `documentId`, `contentHash` (SHA-256 текста
чанка, считается этим модулем самостоятельно — не полагается на то, что `chunkId`
у `library-text` сам является хэшем содержимого), `providerId`, `model`,
`dimension`, `vector` (BLOB, `Float32Array`), `createdAt`/`updatedAt`. Эмбеддинг
считается актуальным только при совпадении ВСЕХ четырёх: `contentHash`,
`providerId`, `model`, `dimension` — смена модели или провайдера никогда не
позволяет молча использовать старый вектор.

### Incremental indexing (`runEmbeddingIndex`)

Курсор по `rowid` в `chunks` (`WHERE rowid > ? ORDER BY rowid LIMIT ?`) —
библиотека никогда не грузится в память целиком. Прогресс (`running`/`pid`/
`stopRequested`, счётчики `total`/`processed`/`reused`/`embedded`/`failed`/
`skipped`/`orphanRemoved`) хранится в той же БД по образцу
`TextStore.claim()`/`progress()` — resume после прерывания и защита от двух
одновременных прогонов работают идентично этапу 2. Каждый счётчик имеет ровно
один смысл (см. doc-comment в `embeddings/types.ts`): `processed` всегда равен
`reused+embedded+failed+skipped` и никогда не превышает `total`; `reused` —
чанк не отправлялся провайдеру повторно, потому что уже сохранённый вектор
прошёл и валидацию, и проверку согласованности; `embedded` — вектор реально и
проверенно записан в хранилище; `failed` — либо вызов провайдера, либо
валидация вектора, либо запись в хранилище завершились ошибкой; `skipped` —
пустой/только-пробельный текст чанка (не отправляется провайдеру вовсе);
`orphanRemoved` — удалённые записи, чей `chunkId` больше не существует в
`chunks` (отдельно от первых четырёх, считается только после полного, не
sample, прогона). Отказ одного батча у провайдера считается `failed` только
для его чанков и не прерывает прогон.

`computeEmbeddingOverview()` сводит состояние хранилища и провайдера в статус:
`not_configured | empty | partial | ready | stale | rebuilding | error`.

### Semantic retrieval и векторный поиск

**Решение по технологии векторного поиска: чистый JS, без native-зависимостей.**
Никакого native extension SQLite (sqlite-vec/sqlite-vss), никакой отдельной БД
или сервера. `src/services/embeddings/search.ts` — brute-force cosine similarity
по всем векторам текущего provider/model/dimension, загруженным в память для
одного запроса. Причина: единственный способ работать идентично на Mac Intel и
на Windows без компиляции нативного модуля и без внешней инфраструктуры;
стоимость — O(n) по времени и памяти на запрос — измерена бенчмарком на реальной
выборке (см. ниже), а не предполагается для всех 54 958 чанков.

### HybridRetriever (`src/services/rag/hybrid.ts`)

Три режима: `lexical` (только `retrieveChunks()`, этап 3, без изменений),
`semantic` (только векторы), `hybrid` (оба, default). Fusion — **rank-based**
(weighted Reciprocal Rank Fusion, тот же `RRF_K=60`, что и в
`scientific-search/pipeline.ts`), никогда прямая сумма BM25 и cosine similarity:
несопоставимые шкалы. Параметры (`RRF_K`, `RRF_LEXICAL_WEIGHT`,
`RRF_SEMANTIC_WEIGHT`) — константы в `rag/types.ts`, `fuseRankings()` —
чистая, экспортируемая, независимо тестируемая функция.

`FusedChunk` хранит provenance: `lexicalRank`/`semanticRank`/`fusedRank`,
`lexicalScore`/`semanticScore`, `foundBy: 'lexical'|'semantic'|'both'`.
Дедупликация — по `chunkId` (`Map`), тай-брейк при равном fused score — по
`chunkId` (детерминированный порядок).

Безопасная деградация: если провайдер/хранилище эмбеддингов недоступны, пусты
или запрос к ним упал — `hybrid`/`semantic` автоматически становятся `lexical`,
с `fallbackReason` в диагностике; падения не происходит никогда.
`RagResult.mode` — реально использованный режим (может отличаться от
запрошенного), не только в dev-диагностике.

### Что не меняется в существующем RAG grounding

`buildContext` (жёсткий бюджет), `validateAnswerGrounding` (claim-level,
citation только для реально вошедшего evidence), защита от prompt injection —
не тронуты: `hybridRetrieve()` возвращает `FusedChunk[]`, структурно являющийся
`RetrievedChunk[]`, и `context.ts`/`citations.ts` принимают его без изменений.

### UI

В «Спросить библиотеку» — переключатель «Поиск»: Гибридный (default) / По
смыслу / По словам. Если выбран Гибридный/По смыслу, а семантический индекс не
построен или недоступен — обычный (не только dev) баннер: «Семантический индекс
пока не построен или недоступен - используется поиск по словам (FTS5)».
В dev-диагностике — режим, количество кандидатов FTS/semantic/после fusion,
время каждого этапа, покрытие embedding-индекса, число устаревших записей,
причина деградации, и происхождение (`FTS`/`Semantic`/`FTS + Semantic`) каждого
показанного фрагмента.

### Этап 4.1: аудит корректности (векторы, консистентность, orphans, ошибки)

Независимый аудит выявил 12 проблем в реализации этапа 4; все исправлены в
одном раунде, без изменения RAG grounding/citations и без новых зависимостей.

- **Единый валидатор** `src/services/embeddings/vector.ts`
  (`validateEmbeddingVector`) применяется на всех границах: ответ провайдера,
  запись в хранилище, чтение из хранилища, перед cosine similarity и на этапе
  reuse-проверки. Отвергает не-массивоподобные значения, несовпадение
  фактической длины с ожидаемой размерностью, любой нечисловой/NaN/±Infinity
  элемент и нулевой вектор (norm=0). Повреждённый сохранённый вектор никогда
  не считается пригодным для reuse — обрабатывается как отсутствующий и
  переэмбеддится.
- **`cosineSimilarity`** (там же) больше не использует
  `Math.min(a.length, b.length)`: векторы разной длины — явная ошибка, не
  молчаливое усечение. Результат всегда конечное число (regression-тест:
  `dimension=2` при фактической длине вектора 1 не даёт `similarity=1`, а
  ошибку/пропуск).
- **`chunkConsistencyChecker`** (`src/services/rag/hybrid.ts`) — до
  использования эмбеддинга проверяет, что `chunkId` существует, что реальный
  `documentId` чанка (не тот, что записан в самой строке эмбеддинга) совпадает
  с сохранённым, и что текущий SHA-256 текста чанка совпадает с сохранённым
  `contentHash`. Гидратация (`hydrateChunk`) вызывается только для чанков,
  прошедших эту проверку, — метаданные документа всегда берутся из реальной
  связи chunk→document, а не из независимого поля эмбеддинга.
- **Coverage и orphans**: `EmbeddingStore.validCount()` считает
  `embeddedChunks` только по строкам, у которых валиден вектор И совпадают
  provider/model/dimension/contentHash/document-связь. `semanticSearch()`
  применяет валидацию и `isConsistent` к каждому кандидату ДО top-K —
  orphan/stale запись никогда не может вытеснить настоящий результат из
  top-K и никогда не появляется в выдаче; `SemanticSearchOutcome`/
  `RetrievalDiagnostics` сообщают `invalidVectorCount`/
  `inconsistentCandidateCount` явно.
- **`OpenAIEmbeddingProvider`**: векторы сопоставляются с `input[]`
  исключительно по `data[].index` (никогда по позиции в массиве ответа).
  Дублирующийся, отсутствующий или выходящий за диапазон `index` — ошибка
  провайдера.
- **Разделение ошибок провайдера и хранилища** в `runEmbeddingIndex()`: вызов
  провайдера, валидация вектора и запись в хранилище — три независимо
  перехватываемых шага. Запись батча теперь атомарна
  (`EmbeddingStore.upsertBatch`, одна транзакция `BEGIN IMMEDIATE`/`COMMIT`/
  `ROLLBACK`); при ошибке записи `countActuallyStored()` перепроверяет
  хранилище напрямую, чтобы `embedded`/`failed` отражали реально сохранённое,
  а не предположение об атомарности, и прогон останавливается без дальнейших
  обращений к провайдеру.
- **Семантика счётчиков прогресса** — см. секцию Incremental indexing выше:
  каждый из `total`/`processed`/`reused`/`embedded`/`failed`/`skipped`/
  `orphanRemoved` имеет ровно один недвусмысленный смысл; `skipped` — реальный
  случай (пустой чанк), а не мёртвый счётчик.
- **Производительность**: без native-зависимостей и внешней vector DB.
  `validateEmbeddingVector` считает норму один раз и возвращает её вместе с
  вектором, чтобы `cosineSimilarity` её не пересчитывал; ранжирование — через
  ограниченный `topK()` (частичная вставка с бинарным поиском в буфере
  размера `limit`), а не полная сортировка всех кандидатов.

Бенчмарк (детерминированный провайдер, реальный текстовый индекс только на

### Этап 5: process-local vector cache

Контролируемое измерение на 10 000 чанков × 1536 (см. бенчмарк ниже) показало,
что доминирующая часть времени semantic-запроса — не cosine similarity и не
top-K (оба уже дёшевы), а (1) повторное чтение и декодирование BLOB-векторов
из SQLite на КАЖДЫЙ запрос и (2) — что оказалось даже дороже — повторная
подготовка (`db.prepare`) одного и того же SQL-запроса согласованности
(`chunkConsistencyChecker`) на каждую из тысяч строк-кандидатов при каждом
запросе. Второе исправлено отдельно и без риска (см. ниже); первое устраняется
новым, полностью опциональным in-memory кэшем `src/services/embeddings/cache.ts`.

**`VectorCache`** — один кэш на процесс (`processVectorCache`, но используется
только там, где явно передан — см. ниже), хранящий уже провалидированные
`{chunkId, documentId, contentHash, vector, norm}` для ОДНОЙ комбинации
`rootId::providerId::model::dimension`. Гарантии:
- в кэш попадают только строки, прошедшие `validateEmbeddingVector` И (если
  передан) consistency-checker — corrupted/stale/orphan-записи никогда не
  кэшируются;
- на каждый `getOrLoad()` сверяется `EmbeddingStore.dataVersion()` — durable
  счётчик в таблице `settings`, увеличиваемый КАЖДОЙ записью (`upsertBatch`/
  `remove`), в том числе из другого процесса (индексирование обычно идёт
  отдельным процессом/CLI, а не в том же, что обслуживает запросы) — при
  расхождении кэш прозрачно перестраивается;
- consistency-checker ПОВТОРНО применяется к каждой кэшированной записи на
  каждом запросе (не только при загрузке) — это ловит случай, когда контент
  чанка изменился, а эмбеддинг ещё не пересчитан (значит `dataVersion` не
  сдвинулся, но запись уже устарела);
- сбой при загрузке (искл. из `store.currentRows()`) НИКОГДА не пробрасывается
  — `getOrLoad()` возвращает `null`, и `semanticSearch()` прозрачно переходит
  на прежний прямой путь через SQLite — поведение при отсутствии/сбое кэша
  побайтово совпадает с поведением до появления кэша;
- строго opt-in: `semanticSearch()`/`hybridRetrieve()`/`askLibrary()` НИКОГДА
  не подставляют кэш по умолчанию сами — единственное место, где реальный
  процесс-синглтон `processVectorCache` подключается, это сам API route
  (`src/app/api/library/ask/route.ts`); это осознанное решение после того, как
  автоматическая подстановка кэша по умолчанию сломала уже существующие тесты
  (кэш, ключуемый по `rootId`, а не по идентичности инстанса, иначе не имел бы
  смысла между запросами — но это же значит, что два независимых теста с
  одинаковым `rootId="test"` и разными физическими store начинают
  ошибочно "видеть" чужой кэш, если кэш подставляется неявно).
- пользовательский ТЕКСТ в кэше не хранится — только технические поля,
  необходимые для ranking и повторной consistency-проверки.

**`EmbeddingStore.dataVersion()`** — новый метод/durable-счётчик (таблица
`settings`, ключ `dataVersion`), увеличивается в той же транзакции, что и
`upsertBatch`/`remove`.

**`chunkConsistencyChecker`** — статичный `db.prepare(...)` теперь готовится
ОДИН раз при создании чекера, а не при каждом вызове; на 10 000 записей это
дало ~700 мс экономии на запрос (было — единственная большая статья расходов).

### Бенчмарк 10 000 × 1536 (до/после)

Тестовый provider — `DeterministicEmbeddingProvider` (без сети), временное
изолированное SQLite-хранилище (никогда не реальный `.local-data`), реальный
текстовый индекс — только на чтение.

| сценарий | median | p95 | max |
|---|---|---|---|
| до (без кэша, БЕЗ фикса prepare) | ~900 мс | ~1000 мс | ~1470 мс |
| до (без кэша, С фиксом prepare) | 908 мс | 995 мс | 1470 мс |
| после (с кэшем, warm) | 599 мс | 656 мс | 724 мс |
| cache cold-load (разовая стоимость) | 895 мс | — | — |

Экономия в warm-режиме — ~310 мс/запрос (~34%), что соответствует ожидаемой
экономии на декодировании ~10 000 BLOB (см. разбивку по фазам в отчёте). Полная
разбивка по фазам (SQLite read+decode / validate+cosine / top-K) и результаты

дублируются здесь, чтобы не расходиться при последующих прогонах).

### Этап 6: process-local consistency cache (устранение найденного ограничения)

Ограничение, зафиксированное в конце Этапа 5, устранено новым
`src/services/rag/consistency-cache.ts` — тем же opt-in-паттерном, что и
`VectorCache`. Ключевое наблюдение, делающее это безопасным: `chunks.id` в
`library-text` — это `sha256(documentId:ordinal:text)` (см. `chunk.ts`), а
`chunks.text` НИКОГДА не обновляется на месте (только `INSERT`/`DELETE`, см.
`TextStore.replace()`/`remove()`) — значит для ЛЮБОГО всё ещё существующего
`chunkId` его текст гарантированно (с точностью до SHA-256-коллизии) тот же,
что и при создании строки. Из этого следует: `sha256(text)` можно посчитать
ОДИН раз и переиспользовать на каждом следующем запросе, а не пересчитывать
заново — что и делает `ConsistencyCache`, инвалидируясь через новый durable
`TextStore.dataVersion()` (тот же паттерн, что у `EmbeddingStore`, увеличивается
в `replace()`/`remove()`). Все существующие гарантии сохранены: orphan-detection,
documentId-match, hash-match — теперь просто через `Map`-lookup вместо
SQL-запроса на каждую строку.

Замер (см. финальный отчёт задачи «оптимизация consistency/hydration path» за
полными числами): доминирующей статьёй расходов semantic-запроса на 10k/25k
были НЕ vector scan/cosine (уже дёшево благодаря `VectorCache`) и НЕ top-K
(уже дёшево), а именно consistency-проверка — ~586 мс из ~609 мс общего
времени на 10k. После `ConsistencyCache` (warm) — единицы-десятки мс, hybrid
end-to-end стал практически не зависеть от размера embedding-выборки (366 мс
на 10k против 377 мс на 25k), поскольку кэш загружает ВЕСЬ текстовый индекс
целиком один раз (его размер фиксирован — 54 958 chunks), а не растёт вместе
с покрытием эмбеддингами.

### Этап 7: FTS latency outliers — измерение и устранение

Профилирование ~150 запросов разных типов на реальном индексе (54 958 chunks)
показало редкие многосекундные выбросы (max 1399 мс) при в целом быстрой
медиане (~77 мс). Разбивка по фазам показала: `count(*) MATCH` — всегда <5 мс
независимо от частоты термина; сама FTS5-ранжировка (`ORDER BY bm25(...)
LIMIT 20`) — стоимость пропорциональна СУММЕ частот КАЖДОГО отдельного
термина в запросе (не размеру финального AND-пересечения!) — у SQLite FTS5
нет эффективного top-k-by-bm25 short-circuit; `snippet()` — заметная, но не
доминирующая добавка (~20–30% сверху) один раз bm25-ранжировка уже ограничена;
hydration (только top-8/20) — не bottleneck (~6–9 мс); OFFSET — отдельный
источник (2.6+ сек на offset=10000), т.к. bm25-порядок не индексно-бэкенный.

**Найденные патологические сценарии** (реальные слова из корпуса): "a"
(92% chunks), "of"/"the"/"is" (76–88%) — уже были в стоп-словах
`rag/retrieve.ts`, но fallback-ветка `extractSearchTerms` (для вопроса,
состоящего ЦЕЛИКОМ из стоп-слов) ошибочно пропускала их обратно
нефильтрованными — исправлено. Несколько умеренно частых терминов (по
9–23 тыс. совпадений каждый), объединённых через AND (обычный многословный
вопрос) — тоже медленно, независимо от размера итогового пересечения.
Fallback-путь `retrieveChunks()` (до 6 отдельных full-search на термин при
пустом строгом AND) — сумма нескольких умеренно-дорогих запросов, не
единичный патологический случай.

**Исправления** (`library-text/store.ts`, `rag/retrieve.ts`):
- `search()` — дедупликация повторяющихся токенов; безопасный
  candidate-budget (`RANK_CANDIDATE_BUDGET=25000`, сумма частот терминов) —
  при превышении ранжирование переключается на `ORDER BY rowid` (измерено:
  единицы мс независимо от частоты, вместо полного bm25 по всем строкам);
  жёсткий потолок глубины пагинации (`MAX_SEARCH_OFFSET=500`) с тем же
  fallback при большом offset. Всегда явный `rankingDegraded: boolean` в
  результате — деградация ранжирования никогда не скрывается.
- `extractSearchTerms()` — fallback-ветка больше никогда не пропускает
  известное стоп-слово, даже когда весь вопрос состоит из них.
- `retrieveChunks()`/`collect()` — строгий AND строится ИНКРЕМЕНТАЛЬНО с
  остановкой перед превышением 500 символов (не выбрасывается целиком при
  превышении), детерминированно; fallback сортирует термины по возрастанию
  частоты (более редкие — и более информативные — идут первыми) и уменьшен
  до 4 терминов (`MAX_FALLBACK_TERMS`), ограничивая сумму нескольких
  full-search вызовов.

**Snippet/hydration**: исследовано отдельно — после устранения bm25-стоимости
для патологических случаев обе фазы остаются недорогими (snippet — та же
дешёвая rowid-ranked ветка; hydration — уже была ограничена top-`limit`).
Разделение snippet на отдельный запрос НЕ потребовалось — корневая причина
была в ranking, не в snippet как таковом.

**Бенчмарк (150 запросов, комбинированно, до/после)**:

| | median | p95 | p99 | max |
|---|---|---|---|---|
| до | 283 мс | 537 мс | 793 мс | 1399 мс |
| после | 41 мс | 215 мс | 245 мс | 286 мс |

Hybrid retrieval (30–50 запросов) не деградировал; RRF/citations/context
budget не тронуты. Worker Thread не потребовался: событийный цикл теперь
блокируется на ≤~300 мс в худшем FTS-случае (было до ~2.6 сек на глубоком
offset), с оговоркой, что остаточная стоимость сложных многотерминовых
AND-запросов (~150–250 мс) — не устранённое до нуля, а осознанно принятое
ограничение (дальнейшее устранение потребовало бы corpus-частотного
исключения терминов из САМОГО строгого AND-запроса, не только переключения
ранжирования, — не делалось в этом раунде без явной необходимости).

### Внешние зависимости

Не добавлено ни одной новой npm-зависимости и ни одного native-модуля — весь
этап реализован на встроенном `node:sqlite`, `node:crypto`, `node:worker_threads`
(только в прототипе-бенчмарке, не в продакшн-коде) и чистом JS.
